A Node.js/Express + SQLite (sql.js) web app for American Safety Options — staff scheduling, overtime calculation, payroll (with real IRS bracket-based federal withholding), employee self-service, PTO, and clock in/out with per-house staffing caps, supervisor override, and full admin review. ## THIS SESSION (latest) — ADP match rebuilt on the owner's audit workbook (shift-period matching, six-tab audit, Excel download)

The owner sent his own Excel audit (`ASO_Time_Audit_2026-09-27_to_2026-10-03.xlsx`) and said "this is how I want the ADP to match the shift period". The matcher and the page were rebuilt to produce that workbook. **Everything in the older ADP section below about tiers "Ready / Suggested / Needs review", minute-based tolerance on clock times, and `adpInferFromErrors` is superseded by this section.**

- **Matching model (`adpCompareStaff(adpEntries, shifts, tolMinutes)`)**: a punch is a candidate for a shift when they overlap by at least 30 minutes and at least 25% of the shorter one; pairs are taken greedily by overlap. A leftover punch within 30 minutes of an already-matched punch is joined to it (`adp.parts`). The verdict is on HOURS: `match` when |ADP hours − timesheet hours| is within the tolerance (default 15 min), else `differs`. An unusable punch (zero-length, under 0.25 h, or no out) is pinned to the nearest unpunched shift within 2 hours as `incomplete`; otherwise it is `adp_zero` (stray). Remaining shifts are `ts_only` (No ADP punch); remaining usable punches are `adp_only`.
- **`adpClassify(row)`** maps status to tier + label: match→ok "Match", differs→review "Hours differ", ts_only→hold "No ADP punch", incomplete→hold "Incomplete ADP punch", adp_only→suggest "ADP, not on timesheet", adp_zero→blocked "Stray ADP punch".
- **`adpFindings(person, ctx)`** writes the plain-language "What I found" note on every row. **`adpTimesheetChecks(input)`** produces the Timesheet Checks tab (overlaps, over-40 with no OT, shift over 16 h, back-to-back, coverage gaps, empty days, house missing). Coverage only runs for a house whose timesheet covers ≥60% of the hours in range; `input.edge` carries shifts dated the day before/after so an overnight from the previous night is not a false gap; with no prior-day data the first morning is assumed covered to 6 AM; a gap that swallows whole days is split into "House/day with no entries" plus the partial gaps; `input.over` (punches matched to a shift at that house) is used only to name who ADP shows in a gap.
- **Audit view** (`adpAuditSpec(b)` → `adpAuditHtml(b)`, default view after upload) has the workbook's six tabs: Summary, Shift Match, ADP Not On Timesheet, ADP Punches, Staff Totals, Timesheet Checks. **`adpExportAuditXlsx`** lazy-loads ExcelJS 4.4.0 from cdnjs and `adpWriteAuditXlsx(spec, ExcelJS)` writes the same six sheets, with the Result column as a formula driven by `Summary!$B$4` (tolerance) and conditional-format colours E2EFDA / FFF2CC / F8CBAD, header fill 1F3864.
- **Controls**: `#adp-review-min` is now "Match when hours are within" (5/10/15/30, default 15); new `#adp-skip-admin` ("Don't audit office (Admin) punches", default on — ADP Administrative-department punches with no timesheet shift are marked `r.na` and appear on ADP Punches only). Staff on the timesheet with no ADP card are included as pseudo-people (`noCard: true`).
- **Worklist** kept, on the new tiers; `adpMarkAllReviewed` reviews all of one person's open lines with one reason. Per-house audit/sign-off unchanged in behaviour.
- **Verified against the owner's real files**: with his real ADP PDF and a database rebuilt from his workbook's Shift Match tab (35 staff, 117 shifts), the page gives 117 shifts = 50 Match / 13 Hours differ / 50 No ADP punch / 4 Incomplete, 21 ADP-not-on-timesheet, 9 staff with no ADP card — identical to his workbook, row by row for Shift Match columns A–I. The downloaded xlsx recalculates in LibreOffice with the same numbers and no formula errors. Timesheet Checks finds everything his workbook lists (the Kollie overlap, the seven over-40 staff, the 22-hour entry, the back-to-backs, the Serah/Atima/Usene overnight gaps, Serah's empty Saturday, the Gabriella late start, William House missing) plus three extra true ones (Benjamin Sun 6 AM–12 PM, Usene Sat 10–11 PM, Kollie's 25.5-hour run).
- **Tests**: `test-adp-match.js` rewritten for the new model — 95 checks (parser, names, shift-period matching, "What I found" notes, timesheet checks, house suggestion, audit state).
- **Honest limits**: "round-the-clock" is inferred from the data (≥60% covered), not a setting per house; the 6 AM assumption for the first morning is a convention; "Hours over 40" on Staff Totals is a flag, not pay — the system still pays OT after `PAY_CONFIG.otThreshold` per period. ### ADP Timecard Match (`page-adpmatch`, nav under Main, admin + supervisor; custom roles need `shifts_edit`)
The owner uploads the ADP "Timecard Report" PDF; the page matches every punch to the Timesheet Log and corrects the ticked rows to the ADP time.
- **Reading the PDF** happens in the browser with pdf.js 3.11.174, lazy-loaded from cdnjs only when a file is chosen (`adpLoadPdfJs`). The file is never sent to the server. `adpParseTextPages(pages)` takes `{str,x,y}` text pieces per page. ADP prints every cell at the same x as its column heading, so values are classified by the heading they sit under — that is what keeps an overtime-only row from being read as regular time. Verified against the owner's real 36-employee file: 36 employees, 134 punches, and every employee's punches sum exactly to ADP's own "Total Paid Hours".
- **Punch errors**: in and out at the same minute with 0:00 paid (`entry.zero`). The first parser version read these as 24-hour shifts — caught by the totals check. They are shown as `adp_zero`, never paired, never corrected from, and every row on that day gets `adpIssue` so the timesheet shift cannot be rejected from this page.
- **Names**: `adpMatchName(adpName, STAFF, savedMap)` — ADP prints "Last First M". Exact, then last name + first initial if unique (flagged "please confirm"), else unmatched and the user picks from a dropdown. Picks are kept in `localStorage['aso_adp_name_map']` (per computer, deliberately not in the database).
- **Comparing**: `adpCompareStaff(adpEntries, shifts, tol)` pairs within a day by nearest start (within 4h, or any overlap). Statuses `match` / `differs` / `adp_only` / `ts_only` / `adp_zero`.
- **Applying** (`adpApplySelected`): only ticked rows, after a confirm. Rejects first (via the existing `/api/shifts/:id/reject`), then time changes, then adds. Same guards as a manual edit (locked period, `findOverlappingShift`). Changed shifts get `_corrected` and `adpCorrected:{from,hours,at}` (kept through the shifts `extra_data` catch-all). Added shifts get `source:'adp'` and the staff member's home house. One `ADP_CORRECTION` audit entry per change, one `dbSave()` at the end. Nothing is deleted. No server change was needed.
- **Best-practice pass (owner said "implement the best practice")** — the page no longer just lists differences; it sorts them and tracks them to sign-off:
  - `adpClassify(row, reviewMin)` → tier `ok` / `auto` (≤ reviewMin minutes, pre-ticked) / `suggest` (ADP only) / `review` (> reviewMin, missing out punch, or rebuilt shift) / `hold` (timesheet only — kept and paid, reject only by an individual tick) / `blocked` (0:00 punch-error line). `adpCompareStaff` is now always called with tolerance 0; the old "count as a match within" setting is gone, replaced by `#adp-review-min` (default 15).
  - `adpInferFromErrors(entries)` — exactly two 0:00 lines on one day, 1–16 h apart, become one proposed punch (`inferred:true`), always tier `review`.
  - `adpSuggestHouse(staff, date, SHIFTS)` — same weekday over the previous 56 days, then any day, then home house; returns `{house, why}`. The user can override per row (`_adpHouse`).
  - Pay/OT effect: `adpBuild()` copies `SHIFTS`, applies every proposed correction to the copy, and runs the real `computeShiftsWithOT()` once on it (swapping the global inside try/finally). Never write a second overtime calculation for this.
  - **State lives in the Audit Trail, not a new table**: `ADP_REVIEWED` / `ADP_REVIEW_UNDONE` (meta starts `key=<row key>`), `ADP_SIGNOFF` / `ADP_REOPEN` (meta starts `range=<from>..<to>`). `adpAuditState(AUDIT_LOG, from, to)` replays them in time order. Verified: `/api/audit-log/verify` stays intact after 66 corrections + 18 reviews + a sign-off, and sign-off survives a fresh login and re-upload. Caveat: the client keeps only the newest 2000 audit entries, so very old decisions eventually age out of the page (they remain in the database).
  - Sign-off needs zero open items (every row applied, matched, or marked reviewed with a typed reason; unmatched ADP names mapped or left out). It closes the week on this page only — it does not lock the Timesheet Log.
  - `adpReportHtml(b)` — the Reconciliation Report (9 sections), and `adpProcedureHtml()` — a one-page manager procedure marked "Draft for management approval". Both reuse the `.sr-sheet` paper styles and print through `body.adp-printing`.
  - `adpPatterns(people)` — per-person missed/early/late counts and per-house difference totals, from the current file only.
- **Per house** (`#adp-house`): `adpBuild()` tags every row with `rowHouse` (shift location → suggested house → home house) and, when a house is chosen, keeps only that house's rows and recomputes each person's hours from them. Sign-off is per scope: `adpAuditState(log, from, to, house)` matches meta `range=a..b house=Name ·` for one house and `range=a..b ·` for the whole week (the trailing separator stops one matching the other). Rows carry `r.signed`, so a signed house is locked even in the All-houses view. Unmatched ADP names have no house and are only handled under All houses.
- **Whole people missing from one side**: `adpWhoIsMissing(people, unmatched, noCard)` (pure) gives `adpOnly` (ADP punches, no timesheet shifts — including ADP names that are not staff here) and `tsOnly` (timesheet hours, no ADP punches). ### Bug 1 — pay period boundaries were computed in milliseconds (clock-change bug)
`getPeriodForDate()` and four siblings did `anchor + N * periodDays * 86400000`. A day is not always 24h. With a summer anchor, every winter period's Date objects sat at 11 PM the night before, so `fmtPeriod()` (local getters) labelled periods one day early from the Oct 24 – Nov 6, 2026 period onward. With a winter anchor it was worse: `Math.floor` on a diff that is one hour short put the FIRST day of every summer period into the PREVIOUS period, changing which hours count toward OT. Fixed with three shared helpers — `calendarDayDiff`, `periodIndexForDate`, `periodBoundsByIndex` — and `getPeriodForDate`, `getPeriodDatesWithOffset`, `autoAdvancePeriod`, `updatePeriodPreview`, `getPeriodsAroundToday` now all go through them. The payroll week-1/week-2 split and the "days left" counters got the same treatment. Proven with `TZ=America/New_York` for both a May and a January anchor (10 checks in `test-staff-report.js`). **Any new period math must use these helpers, never `* 86400000`.**

### Bug 2 — "Print Timesheet" printed every page of the app
The print stylesheet had `.page { display:block !important; }`, which un-hid all 19 pages (23 sheets of paper in the test database). Now `.page.active`. Confirmed by rendering the print output: 2 pages, Timesheet Log only.

### Bug 3 — a fresh database could never be logged into
Commit 73734db moved the seed admin password to `SEED_ADMIN_PASSWORD` and bcrypt-hashes it at startup — but `saveDB()` then hashed that hash again for any "new" user row, so the stored value never matched. Existing databases were unaffected; a brand-new one was locked out, and `test.js` had been crashing at its third check ever since. `saveDB()` now stores an already-bcrypt value as-is, and `test.js` passes `SEED_ADMIN_PASSWORD` to its scratch server. Back to 117 passed.

### Not done / worth doing next

- `staff_view_wage` should be enforced on the Timesheet Log, Report Builder and server-side load for custom roles too.
- Employees cannot open their own timesheet report from My Schedule & Pay. An electronic "I reviewed this" acknowledgement there would replace the paper signature.

## EARLIER — a full permission-system audit: inventoried every endpoint, every defined permission, checked each for real enforcement

Asked to do a "full and deep audit... check every function and logic flow." ### Found a real, meaningful class of bug: permissions that exist but do nothing
Several permissions were offered as grantable to a custom role, but the underlying endpoint never actually checked them — hard-coded to `requireAdmin` regardless. This means an admin could create a role, grant it "Adjust PTO Balances," and that role would still be silently blocked, because the endpoint was checking `role === 'admin'` directly and had no idea the permission system existed. Found and fixed:
- **`staff_pto_adjust`, `data_backup`, `data_export`** — wired up to their actual endpoints via a new `requirePermission()` middleware (mirrors `requireAdmin`'s shape).
- **`taxes_manage`** — a subtler version of the same bug: the Taxes & Benefits *page* was gated by `taxes_manage` client-side, but the *save* was checked against `payroll_run` server-side, so a role with only `taxes_manage` could see the page and fill out the form, then have every save silently rejected. Split `authorizeSave()`'s PAY_CONFIG check to match the real page boundaries (pay-period fields need `payroll_run`, `defaultDeductions` needs `taxes_manage`).
- **`payroll_unlock`** — added as a genuinely separate permission from `payroll_run`, so being able to run a new payroll period doesn't automatically grant the ability to undo one someone else already finalized.
- **`audit_verify`** — wired up (was hard-coded admin-only despite being read-only and low-risk).
- **`data_reset` / `data_import`** — the opposite fix: these two are genuinely too destructive to ever delegate, so rather than wire them up, removed them from the assignable taxonomy entirely. They stay hard-coded to `requireAdmin` as a deliberate, permanent safety backstop — and now the UI can't show a checkbox that looks like it grants something it never would.

Verified every one of these with real HTTP requests (a role granted only the specific permission can do the thing; the same role without it is blocked; admin's behavior is completely unchanged throughout — confirmed by the full test suite staying green after each individual change, not just at the end).

### The same class of gap, found again on the client side
Checked `userCan()` — the client-side equivalent — for the same pattern: actions defined in its permission map but never actually called anywhere to gate a button. Found `manageStaff` was defined but unused: the Staff Register page's Add/Edit/Deactivate/Delete buttons had no visibility gating at all. Someone with only `staff_view` (not `staff_manage`) could navigate there, see and click every button, and get a confusing server rejection instead of the UI simply not offering something they can't do. Fixed for Staff Register specifically (the highest-impact page) — the Add form and per-row action buttons now correctly hide for view-only access, replaced with a plain "View only" label, while the table itself stays fully readable. Verified through a real browser with an actual `staff_view`-only custom role, not just reading the code.

**Not yet done**: the identical pattern likely exists on Locations, Users/Passwords, Data Manager, and Pay Config pages too (`manageLocations`, `manageUsers`, `dataManager`, `payConfig` are also defined-but-unused in the same `userCan()` map). Staff Register was fixed first as the highest-impact page; the others are a well-scoped, mechanical follow-up using the exact same pattern just demonstrated.

### A test bug I introduced and fixed, worth documenting for anyone touching this file
While adding the tests above, one hardcoded a staff ID ("S001") assuming it would exist throughout the entire sequential test run. It doesn't — an earlier, legitimate test intentionally replaces the whole staff table with a minimal set for its own isolated purposes, and nothing restores the original afterward (correct for that test, but means nothing later in the file can assume the original seed data still exists). ## EARLIER THIS SESSION — a genuinely important gap found by testing feature interactions, not just re-checking known areas

Asked to "fix all gaps" again. Rather than re-verify things already covered, deliberately looked at how the *newer* features (salary/external pay types, the inactive-staff-flag system) interact with each other — that's reliably where gaps hide, since each feature gets tested in isolation but the intersection often doesn't.

### Salary/External staff who go Inactive were being silently erased from payroll entirely — worse than the bug the flag system was built to prevent
Confirmed with a direct test before touching any code: an Inactive salaried or externally-paid staff member produced **no row at all** in the payroll table. Not $0, not a flag, not a warning — nothing. The reason: `buildPayrollDetailRows()` generated rows for these two pay types only when `status === 'Active'`, since they have no shift records to derive a row from the way hourly staff do. The entire inactive-staff-flag system that exists specifically to prevent silent inclusion/exclusion never even got a chance to run for these two pay types.

Fixed by generating a row regardless of Active/Inactive status, holding pay at $0 with a visible "⚠️ INACTIVE — NEEDS REVIEW" badge until an admin explicitly approves it via the same flag mechanism hourly staff already use, and extending `detectAndFlagInactiveStaff()` to actually detect these two pay types (salary staff get flagged for the current period, since their pay isn't period-specific the way a worked shift is; external staff get flagged for whatever period they already have a real entry for). Payroll finalization now blocks on this too, matching hourly.

Verified at three levels: an extracted-function test reproducing the exact broken scenario (now fixed), the full test suite (110 passing, zero regression), and a real browser confirming the badge and $0 actually render — not just that the underlying data is correct. Added a new permanent `test-payroll-inactive-interaction.js` (9 checks) covering this specifically, including an edge case worth calling out: a *denied* flag must still hold pay at $0 exactly like a missing one — denied and approved are not the same thing, and it would be easy to accidentally treat "reviewed" as equivalent to "approved."

### A genuinely useful lesson from this session's browser testing, worth repeating for next time

1. First "failure": employee's page was closed 1 second after clicking Clock In, before the async request had actually completed — the click succeeded, the network call didn't get a chance to.
2. Second "failure": `page.reload()` lost session state in a way a fresh `page.goto()` didn't.
3. Third "failure" (looked like a real bug — the modal submit did nothing): turned out to be **correct server behavior**. The test had both the employee's clock-in and the admin's modal default to "now" within the same couple of seconds, so the clock-out time wasn't genuinely *after* the clock-in time — the 400 rejection was right. Confirmed by intercepting the actual network response (`page.route()` + reading the real response body) instead of just checking the status code.
4. Fourth "failure": created server-side state via a raw `fetch()` call *after* the page had already loaded, then expected the already-rendered page to somehow know about it without reloading — client-side `CLOCK_ENTRIES` is only as fresh as the last load.
**The pattern worth remembering**: when a browser test looks like it's failing, check the actual server response body before assuming the client is broken, and check whether the test itself did something a real user wouldn't (closing a page mid-request, expecting stale client state to update itself, creating two timestamps within the same second and expecting a strict ordering check to reliably distinguish them).
