The user was genuinely stuck: clocked in, couldn't clock out, no way to recover. Screenshots showed a red error toast ("Clock-out time must be after your clock-in time") and a Timesheet full of 0.02-hour test entries from repeated attempts to work around it.

### Root cause: clock times were only tracked to the minute
Clocking in and out within the same clock-minute — trivially easy by testing the buttons, or a fast double-tap — computed to exactly 0 hours, which was then rejected as "before your clock-in time." The person was stuck until the minute ticked over, and stuck again if it happened twice. Fixed the actual precision to seconds, on both server and client. **Verified against the user's exact scenario, twice**: once via direct API calls (40 seconds apart in the same minute — now succeeds), and once with a real browser reproducing the literal click sequence (Clock In, then Clock Out immediately after) — no more stuck error.

**Caught a second bug my own fix introduced, before shipping it**: the display that shows "Recent Clock History" used `calcHours()`, an existing function correctly designed for plain HH:MM shift times — but it compares at minute granularity, so two now-second-precise times in the same minute both round to the same value, tripping its "assume overnight, add 24h" heuristic. A near-instant clock in/out was displaying as 24 hours. Fixed by building a separate, purpose-built `calcClockHours()` (mirroring the server's date-aware, second-precision math) rather than changing `calcHours()`, which is correct for its actual use case (real shifts, never carrying seconds) and shouldn't be touched. Re-verified with the same real-browser reproduction — now correctly shows a tiny fraction of an hour, not 24.

### A genuinely useful lesson from this session's browser testing, worth repeating for next time
Several browser-verification attempts in a row appeared to fail, and each one turned out to be a *test-harness* mistake, not an app bug — but each one required actually digging in rather than assuming:
1. First "failure": employee's page was closed 1 second after clicking Clock In, before the async request had actually completed — the click succeeded, the network call didn't get a chance to.
2. Second "failure": `page.reload()` lost session state in a way a fresh `page.goto()` didn't.
3. Third "failure" (looked like a real bug — the modal submit did nothing): turned out to be **correct server behavior**. The test had both the employee's clock-in and the admin's modal default to "now" within the same couple of seconds, so the clock-out time wasn't genuinely *after* the clock-in time — the 400 rejection was right. Confirmed by intercepting the actual network response (`page.route()` + reading the real response body) instead of just checking the status code.
4. Fourth "failure": created server-side state via a raw `fetch()` call *after* the page had already loaded, then expected the already-rendered page to somehow know about it without reloading — client-side `CLOCK_ENTRIES` is only as fresh as the last load.
**The pattern worth remembering**: when a browser test looks like it's failing, check the actual server response body before assuming the client is broken, and check whether the test itself did something a real user wouldn't (closing a page mid-request, expecting stale client state to update itself, creating two timestamps within the same second and expecting a strict ordering check to reliably distinguish them).

### The concurrency guarantee is now real, not theoretical
The previous handoff flagged this honestly as unverified: "correct by construction from reading the code, but never load-tested with genuinely concurrent connections." This session actually tested it — and found the reasoning ("Node is single-threaded, so it's probably fine") wasn't good enough to rely on long-term, so it was replaced with something that doesn't depend on that assumption at all.

- **Rewrote `/api/clock/in`'s capacity and double-clock-in checks as a single atomic `INSERT ... SELECT ... WHERE` statement.** The old code did "check capacity in JS, then insert" as two separate steps — safe today only because nothing async happens in between, but one careless future edit (adding an `await` in the wrong place) would silently reintroduce a real race condition. The new version puts both guards (capacity, and "not already clocked in") directly in the SQL statement's `WHERE` clause, so the database itself is the single source of truth for whether a row goes in. `db.getRowsModified()` (verified to work correctly via sql.js) reports whether the atomic insert actually happened.
- **Proved it with genuine concurrency, not sequential test calls**: fired 5 truly simultaneous requests (`Promise.all`, no `await` between them) at a 2-person-capacity house — exactly 2 succeeded, exactly 3 rejected, verified against the raw database file directly. Repeated with 7 requests at a 3-capacity house (exactly 3 succeeded). Separately tested the same person firing 5 simultaneous clock-in requests (the "double-click" scenario) — exactly 1 succeeded, matching a real accidental double-click.
- **Made a real test-setup mistake and caught it before treating it as a server bug**: reused a staff ID between two test users, which made a correct rejection look like a failure. Checked the database before assuming the code was wrong — it wasn't; the test data was.

## Known limitations, stated honestly
- W-4 Step 2 checkbox (multiple jobs) isn't modeled — the calculation always uses the Standard Withholding Rate Schedule. If any staff checked that box on their real W-4, this understates their withholding relative to their actual election. Would need a `w4Step2Checked` boolean and the Step 2 Checkbox tables (Pub 15-T publishes both).
- Local PA Earned Income Tax (Act 32) — genuinely unhandled, flagged on-page.
- No automated test exercises `confirmAndRunPayroll()`'s full DOM-driven flow end-to-end with a bracket deduction selected — the integration test this session covers the core per-employee calculation loop with real data, which is the part that actually mattered, but not the full click-through-the-UI path.
- Concurrency under genuinely simultaneous load (not just sequential test calls) has never been load-tested — the capacity-check code relies on Node's synchronous, single-threaded request handling to naturally serialize simultaneous requests to the same house, which is correct by construction from reading the code, but unverified under real concurrent connections.
- No direct deposit / tax filing / W-2 generation — this is a payroll calculator and record-keeper, not a full payroll processor. Out of scope by design.
